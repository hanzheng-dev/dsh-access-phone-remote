# 远程访问方案

> 手机怎么连到电脑？这里说清三种场景、四条路线、以及为什么现在是这个方案。

---

## 一、问题拆解

"手机连电脑"其实是**三种场景**，难度完全不同：

| 场景 | 难度 | 现在怎么解决 |
|---|---|---|
| **同一个 WiFi** | 🟢 简单 | **UDP 广播自动发现**（已实现，零配置） |
| **不同网络**（4G ↔ 家里 WiFi） | 🔴 难 | 需要 Tailscale（用户装一次） |
| **完全没有网络** | ⚫ 不可能 | —— |

**关键认知**：**难点只在第二种**。而第一种（家里用）已经做到零配置了。

---

## 二、四条技术路线

### 路线 A：内置 Tailscale SDK

**想法**：把 Tailscale 塞进 App，用户不用另装。

**现实**：
- Tailscale **没有面向 Android 的"嵌入式 SDK"**
- 他们官方的 Android 项目（`tailscale-android`）是**一个完整的 App**，不是库
- 有一个 `tsnet`（Go 写的嵌入式版本），理论上能用 **gomobile 编译成 AAR**
- **但**：即使用 tsnet，用户**仍然要登录 Tailscale 账号**（OAuth / device auth）

**评估**：
| 项 | 结果 |
|---|---|
| 工作量 | 🔴 **2-4 周**（含 gradle/gomobile 工具链、登录流程、真机调试） |
| 用户收益 | 少装一个 App |
| 是否免除账号 | ❌ **仍然要 Tailscale 账号** |

**结论**：**收益小、代价大。** 用户少装一个 App，但仍要注册 Tailscale。

---

### 路线 B：自己做 P2P（WireGuard / WebRTC）

**想法**：不依赖 Tailscale，自己做打洞和加密。

**现实**：
- 底层可以用 **WireGuard**（`wireguard-android` 库）或 **WebRTC**（数据通道）
- **但必须自己解决**：
  - **信令服务器**（两端怎么交换地址）
  - **NAT 穿透**（打洞、中继兜底）
  - **身份认证**（谁是谁）
  - **密钥管理 / 轮换**

**评估**：
| 项 | 结果 |
|---|---|
| 工作量 | 🔴 **1-3 个月**（而且需要一台有公网 IP 的服务器做信令） |
| 用户收益 | 不用注册 Tailscale |
| 新成本 | **你要维护一台服务器**（持续成本） |

**结论**：**这是做一个 Tailscale 竞品**，不是做一个小工具该干的事。

---

### 路线 C：端口转发 + 动态 DNS

**想法**：电脑开端口 + DDNS，手机直连。

**现实**：
- 需要**公网 IP**（大多数家庭宽带没有）
- 需要**路由器端口转发**（用户得会配）
- **安全风险高**（把服务暴露到公网）

**评估**：**不推荐**。对普通用户太难，对安全不友好。

---

### 路线 D（★ 当前方案）：分层解决

```
同一 WiFi   → UDP 广播自动发现（零配置）★ 已实现
不同网络    → 引导装 Tailscale（一次，5 分钟）
不想装      → 局域网也能用（只是出门用不了）
```

**为什么这是对的**：
- **解决 90% 的场景（家里）零成本**
- **剩下的 10%（出门）用现成工具**，而 Tailscale 本身很好用、免费、跨平台
- **不引入服务器成本、不重复造轮子**

---

## 三、四条路线对比

| | A 内置 SDK | B 自己做 P2P | C 端口转发 | **D 分层（现在）** |
|---|---|---|---|---|
| 工作量 | 2-4 周 | 1-3 月 | 3-5 天 | **已完成** |
| 免账号 | ❌ | ✅ | ✅ | ❌（出门时） |
| 免装 App | ✅ | ✅ | ✅ | ❌（出门时） |
| 服务器成本 | 无 | **要一台** | 无 | 无 |
| 家里用 | ✅ | ✅ | ✅ | ✅ **零配置** |
| 出门用 | ✅ | ✅ | ⚠️ 需公网 IP | ✅（装 Tailscale） |

## 四、如果你还是想做（路线 A 的具体路径）

**留作参考，但不建议现在做**：

1. **调研 `tsnet` + gomobile**
   - 装 Go 环境
   - `go install tailscale.com/cmd/tsnet` 之类
   - 用 `gomobile bind` 编出 `.aar`
2. **Android 侧集成**
   - 引入 AAR
   - 处理 VPN 权限（`VpnService`）
   - 处理 Tailscale 登录（device auth：显示一个 URL + code，用户在浏览器授权）
3. **服务端侧**
   - 也要接入 Tailscale（用 `tailscale` 命令行或 `tsnet`）
4. **测试**
   - 真机 + 不同网络环境

**最大的坑**：Tailscale 的 Android 实现深度依赖 `VpnService`，
**一个进程只能有一个 VPN 服务** —— 如果用户已经装了 Tailscale App，两个会冲突。

---

## 五、真正值得做的下一步（如果你要"更一体化"）

按性价比排序：

| 优先级 | 做什么 | 工作量 | 收益 |
|---|---|---|---|
| **P0** | ✅ UDP 广播自动发现 | 已完成 | **家里零配置** |
| **P1** | App 内接收文件 → 存相册（免 adb） | 半天 | 去掉对电脑端 adb 的依赖 |
| **P2** | App 内显示"连接诊断"（自检） | 半天 | 出问题用户能自己看 |
| **P3** | 二维码扫码配置（App 内扫码） | 1-2 天 | 省一次手输 |
| **P4** | 集成 Tailscale SDK | 2-4 周 | 少装一个 App |

**P1 和 P2 是"一个 APK 更好用"的关键**，且成本低。
**P4 收益/成本比最差**。

---

## 六、一句话总结

> **"一个 APK 搞定一切"这个目标，卡点不在功能，在网络穿透。**
>
> **而网络穿透这件事，Tailscale 花了整个公司十年在做。**
>
> **我们的正确姿势是：家里做到零配置（已完成），出门借力 Tailscale（一次配置）。**
>
> **把省下来的时间花在"App 内能力"上（P1/P2），比重复造一个 VPN 值得。**
